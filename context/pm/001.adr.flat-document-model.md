## Context

The first data model organized documents in a configured doctype
hierarchy (feature → spec → task) with per-doctype directories, parent
requirements, and structural options. Months of real use showed the
hierarchy fighting reality: documents needed parents of the "wrong"
kind, sibling documents could not depend on each other and got split
with redundant content, and empty container documents existed only to
satisfy structure.

## Decision

There is one document kind. Types (feature, spec, task, adr, note, or
any custom vocabulary) are metadata labels carried by the filename tag,
declared in `pm.json` with optional status overrides. Any type can
parent any type. Groups are bare directories `{id}.{slug}/` that share
the global ID sequence and provide physical organization without
document overhead. The tool enforces referential integrity only;
content structure is guidance (type guides), not configuration.

## Consequences

Easier: free composition, custom vocabularies, agents create the right
document without structural rules, one scanner and one placement rule.
Harder: conventions are soft — nothing stops a project from using types
inconsistently; the guides carry that weight.

## Alternatives considered

- **Keep the configurable hierarchy** — pros: placement guaranteed by
  config, structure is self-documenting. Rejected: the guarantees were
  the source of the friction; users worked around them instead of with
  them.
- **Epics as directory+document pairs** — pros: a container could carry
  its own prose. Rejected: recreates the dual-identity problems (shared
  IDs, two things to keep in sync) that motivated the change.
