Distilled research on comparable tools and their failure modes, done
before the flat-model redesign.

## Layout families

1. **Per-change directories** (GitHub Spec Kit `specs/NNN-branch/`,
   OpenSpec `changes/`): each unit of work gets a folder of artifacts.
   Strong ceremony, good for teams, tends to waterfall.
2. **Living-document tree** (pm, backlog.md): one file per concern,
   edited in place, frontmatter as metadata. Best fit for solo + agent.
3. **Database files** (Task Master `tasks.json`, beads): machine-first,
   merge-hostile, opaque to plain editors.
4. **Constitution/memory systems** (BMAD, Agent OS): global rule files
   steering the agent, orthogonal to work tracking.

## The OpenSpec lesson

OpenSpec keeps truth in `specs/` and work as deltas in `changes/` that
an agent merges back on completion. In practice the two representations
drift — the merge step is agent-executed ceremony that silently
degrades. Conclusion: one living document, with git as the history, is
the durable shape; numbered greppable IDs (which OpenSpec users request)
are a differentiator worth keeping.

## Footguns catalog

1. Two sources of truth that need a merge step.
2. A second file required before work can start.
3. Identity by folder name or heading text instead of stable IDs.
4. Status anywhere but frontmatter.
5. Loading everything into agent context (context pollution).
6. The graveyard: done/stale docs polluting every listing.
7. Merge-hostile database files.
8. Identity coupled to an external service.
9. Skippable ceremony — it will be skipped; design so the lazy path is
   the correct path.
10. Treating the doc as generated output instead of the source.

## Linear lessons

The chronic complaint is one-level nesting (issue → sub-issue only);
free-depth parenting avoids it. Its anti-graveyard mechanics
(auto-archive, aging into a triage queue) are the model for keeping
listings honest without blocking anyone.
